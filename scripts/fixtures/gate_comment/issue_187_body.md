## Goal
A client that stops sending its request body is cut off after an idle timeout. It cannot hold a request, a key reservation or a volume open forever.

## Problem
The server has no timeout on request headers or bodies (only the 10 s TLS handshake in `reactor.rs`), and hyper has none by default. Since #182, compaction waits while a write is landing in a volume. So one PUT above 4 MiB that sends half its body and keeps the connection open keeps that volume busy, and no volume is ever reclaimed (disk-fill DoS). Before #182 compaction went ahead and lost that write instead.

## Requirements
1. One function, `next_frame(body, idle) -> Result<Option<Frame>, Idle>`, in a new module (`server/src/body_timeout.rs`). It wraps `body.frame()` in `tokio::time::timeout`.
2. The three body loops use it: `read_body`, the UploadPart streaming loop and the streamed PUT loop in `server/src/s3_api.rs`. A timeout answers 400 `RequestTimeout` ("Your socket connection to the server was not read from or written to within the timeout period"), drops the writer (its reservation becomes a gap), and closes the connection.
3. The idle time comes from `--body-idle-timeout` (default 60 s; AWS uses about 20 s) and the config file, with the same name in `README.md`'s option list.
4. Header read timeout: `http1().header_read_timeout(...)` in `reactor.rs`, the same default.

## Invariants, each with its test
- A body that pauses for less than the idle time still succeeds: a test sends in two halves with a pause.
- A stalled streamed PUT is cut off: with the idle time set to 1 s, the client gets 400 `RequestTimeout` and `state.volume_writers_in_flight(1) == Some(0)` afterwards. Wait on it, as `compaction_inflight_test.rs` does; no fixed sleeps in assertions.
- After the cut-off, `compact_oldest_volume` is not `busy`.
